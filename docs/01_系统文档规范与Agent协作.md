# 系统文档规范与 Agent 协作约定

文档 ID：`documentation-standard`；规范版本：`1.0.0`；内容版本：`1.0.0`；更新日期：2026-09-18。

适用仓库：`general_video_annotation_level3_v2/extract_full_pipeline`。本规范面向维护这个系统的开发者、不同 Agent 和不同会话。下文的“必须”是文档维护契约；未来校验器、网页和自动化检查均属于待开发能力。

## 1. 新 Agent 从这里开始

系统把视频加工为镜头、全局片段、三级语义描述，再提取人物、声音、物体、场景资产，最后用于结果浏览和生成效果对比。当前没有一个入口包办所有分支；不要看到 `all` 就认为跑完整个系统。

只维护以下三份权威文档，避免重复维护多套系统事实：

| 顺序 | 文档 | 权威范围 | 按需阅读入口 |
|---|---|---|---|
| 1 | 本文 | 文档格式、协作规则、增量阅读、变更交接 | 首次读 §1–§5；更新格式时读 §6–§10 |
| 2 | [全流程 Pipeline 说明](02_全流程Pipeline说明.md) | 实际流程、产物契约、源码映射、分支、已知差异；未来网站内容源 | 先读系统索引，再按模块标记读取 |
| 3 | [结果展示网站设计](03_结果展示网站设计.md) | 网站架构、交互、解析接口、部署、开发验收 | 前端任务读 §1–§5；接口/部署任务读对应章节 |

第一轮行动顺序：读本节 → 检查 Git 状态 → 读文档二系统索引和已知差异 → 选定本次涉及的模块 → 读这些模块及其直接输入输出 → 检查对应源码和一份小样本 → 开始任务。已有文档的结论是导航，不替代修改前的源码核实。

当前应牢记的事实：

- 文档二以“固定上游结构 + Scheme A 描述 + 全局轨迹直接归属”的组合为主要讲解路径，同时保留基础三级描述和 CHR 聚类支路。主要讲解路径不表示已存在完整生产编排器。
- `S1` 只在一个 global 内有意义；完整角色键包含运行、视频、global 和 S-ID。
- `valid` 音频通常表示候选；`status=ok` 通常表示处理完成。二者都不自动代表人工认可或语义正确。
- 本次核验读取了脏工作树和未跟踪文件。只按 HEAD 回看会漏掉 CocktailASR 接入、对齐降级逻辑及当前展示器。
- 仓库 `.gitignore` 当前包含 `*.md`。三份新文档默认被忽略；本次只编写文档，没有改忽略规则、暂存或提交。

向新会话传递任务时，最小入口提示可以是：“工作目录为 extract_full_pipeline；先读 docs/01_系统文档规范与Agent协作.md §1–§5，再按模块 ID 查文档二。任务涉及模块：……；最近核验基线：……；允许修改范围：……”。本文不会自动被所有 Agent 加载。以后若接入仓库 `AGENTS.md`，只增加指向本节的简短入口，不复制正文规则。

## 2. 职责边界与事实层级

| 信息 | 放在哪里 | 不应放在哪里 |
|---|---|---|
| 系统做什么、模块依赖、真实输出 | 文档二对应模块 | 网页组件中硬编码第二份说明 |
| 文档怎么写、Agent 怎么接续 | 文档一 | 每个模块重复一遍 |
| 卡片布局、API、热加载、部署 | 文档三 | 算法源码注释中定义页面导航 |
| 运行次数、成功数、图片、音频路径 | 运行产物；由适配器读取 | 文档二中的常量 KPI |
| 当前实现的行为 | 源码 + 当前样本 | 仅凭旧计划文档推断 |
| 改进建议和未来架构 | 明确标为“设计/待实现” | 写成已上线能力 |

证据分为 `code`（核验源码）、`sample`（核验真实产物）、`design`（本次设计）、`unknown`（未核验）。源码和历史样本不一致时，两者都保留：说明“当前代码如何”“旧运行实际如何”，不要改写历史样本来消除差异。

旧有 `ARCHITECTURE.md`、`PIPELINE_README.md`、`ASSET_CHAIN_README.md`、优化计划等作为背景索引。本文档组负责当前概念和网站契约；旧文档发生冲突时，以对应代码、实际产物及文档二差异登记为依据。既有文档本次未删除或改写。

## 3. 用 Git 降低阅读成本

### 3.1 两种基线，不能混用

`code_baseline` 是文档二核验过的代码提交；`content_version` 是文档自身内容版本。文档提交可能在代码提交之后。脏工作树还要记录关键文件 SHA-256、修改/未跟踪状态，不能写一个 HEAD 就声称完全可复现。

本次基线：`0c5ddfd367388461d96bed16fc57e4560a70ace8`，叠加 2026-09-18 的工作树。精确差异见文档二 `evidence-baseline` 节。历史产物还需要自己的运行来源，不能把本次 HEAD 冒充它们的生产版本。

### 3.2 先列变化，再读正文

在仓库根目录执行下列只读检查。`DOC_BASE` 必须来自文档二系统元数据；变量仅用于本任务。

```sh
git status --short --untracked-files=normal
git rev-parse --show-toplevel
git rev-parse HEAD
git diff --name-status
git diff --cached --name-status
DOC_BASE=0c5ddfd367388461d96bed16fc57e4560a70ace8
git cat-file -e "$DOC_BASE^{commit}"
git diff --name-status --find-renames "$DOC_BASE" HEAD
git ls-files --others --exclude-standard
git check-ignore -v docs/01_系统文档规范与Agent协作.md docs/02_全流程Pipeline说明.md docs/03_结果展示网站设计.md
```

这几项分别覆盖已提交变化、未暂存、已暂存、未跟踪和文档被忽略的情况。不能只看 `git diff HEAD`，也不能只看最后一次 commit。当前仓库还跟踪部分历史 `__pycache__`，它们是阅读噪声，不是运行逻辑的权威来源。

根据文件列表检索文档二各模块 `source_refs`，再看这些文件的局部 diff。新增文件、重命名、删除、共享模块、prompt、输出 schema、默认参数和 CLI 参数都是影响分析对象。未跟踪的 `asset_viewer/` 没有可用的 commit diff，只能比较交接时的哈希/内容。

优先用 `rg` 搜索；环境没有 `rg` 时用 `grep -n`/`find`。本次环境没有 `rg`。例如只读取一个模块：

```sh
sed -n '/^<!-- module:person_align -->$/,/^<!-- \/module:person_align -->$/p' docs/02_全流程Pipeline说明.md
grep -n 'source_refs\|module:' docs/02_全流程Pipeline说明.md
git diff -- global_align_pipeline/global_tracklet_aligner.py
```

基线 commit 不存在时，先检查是否浅克隆或工作目录错误。不能静默改用 HEAD 作为“已核验基线”。可通过已存文件哈希核验局部模块，并把未覆盖范围写入交接。不要为读文档擅自拉取大型仓库或下载模型。

### 3.3 最小影响闭包

阅读集 = 变更模块 + 被改变的输入/输出契约 + 直接消费者。只在契约继续变化时沿依赖继续扩展，不自动读遍所有下游。

| 变化 | 必读范围 |
|---|---|
| 说明措辞、标题、展示顺序 | 本模块 + 文档格式契约；不用读模型代码 |
| 输出路径、字段、时间基准 | 生产模块 + 产物定义 + 直接消费者 + 对应网页适配器 |
| prompt 调整 | 调用入口、输出校验、缓存复用策略、对应模块 |
| `common`、客户端、schema | 系统索引映射到的使用方；检查是否所有入口真使用该公共实现 |
| 仅网页排版 | 文档三对应交互 + Renderer；不用读全部视觉/音频模型实现 |
| 新模块 | 直接上游、输出契约、展示适配方式、受影响运行 profile |

首次了解系统可以扩展阅读，后续应默认按局部证据更新。不要把“先阅读十份长文档”设为每次任务的前置条件。

### 3.4 Markdown 纳入版本管理

采用此文档组时必须显式纳入 Git，否则跨 Agent 无法可靠增量核验。维护者可以在一次文档提交中只强制添加三个确切路径：

```sh
git add -f -- docs/01_系统文档规范与Agent协作.md docs/02_全流程Pipeline说明.md docs/03_结果展示网站设计.md
git diff --cached --stat
```

这是后续采用操作，不是本次已执行动作；执行前须确认暂存区其他改动归属。已被跟踪的文档后续修改能正常进入 diff。若选择调整 `.gitignore`，应单独增加 `docs/` 范围的 Markdown 例外，不顺带解除媒体/权重忽略。本次不修改该配置。

## 4. Agent 工作规范

### 4.1 开发前

明确本次目标、允许改动范围、验收条件和运行分支；保存初始 Git 状态，不覆盖已有修改。读文档二 `known-gaps`，核对所选输入文件存在、schema 与时间基准正确。区分源码路径、运行输出路径、展示整合路径。

不要为了更新说明文档启动 GPU、调用 MiMo、切整片视频、重跑流水线、部署服务或改生产产物。一般只需看源码、小样本和轻量字段统计。对真实算法改动，先用最小有代表性的输入验证，再根据结果决定是否扩展。

### 4.2 开发中

保持模块 ID、产物 ID 稳定；允许改中文展示名和顺序。不随意增加新的版本脚本，先辨认现有 `_v2/_v3/_v4` 的继承关系和实际调用入口。文件后缀不保证它是当前默认实现，也不保证其输出 schema 版本一致。

输出契约变化必须同步文档二；改变解析/展示协议必须同步文档一和文档三。局部重跑使用新的输出目录，并说明复用哪些上游产物；尤其不能直接对已有角色目录调用会整目录重建的 materializer。

模型结果缓存必须有适用前提：输入、prompt、模型配置与校验规则一致。现有脚本的“文件存在/成功行就跳过”不等于内容哈希缓存。改 prompt 后仅加 `--skip-existing` 可能继续看到旧结果。

### 4.3 完成时

交付实现/文档差异、验证结果、未验证内容、受影响模块、下一步。不要把“待接入网页热加载”写成“已经支持热加载”。除非任务要求，不擅自提交、推送或部署。

推荐交接摘要格式（放任务交付或变更记录，不复制大段代码）：

| 字段 | 内容 |
|---|---|
| 目标与结果 | 完成什么、尚缺什么 |
| 基线 | 核验 commit + 脏文件哈希/状态 |
| 涉及模块/产物 | 稳定 ID 列表 |
| 已核验 | 源码入口、样本、必要检查 |
| 未核验/风险 | 具体缺口，不写泛泛“可能有问题” |
| 下一 Agent 起点 | 精确文件、章节、剩余动作 |

## 5. 写作原则

先讲业务问题，再讲输入、决策、输出，最后给实现映射。中文名称应表达功能，例如“人物轨迹归属”比“Stage 1.5”更容易理解。源码名称只出现在实现映射和开发说明中。

顺序按读者理解安排；依赖由机器元数据确定。声音和视觉可以并行，不能因为页面排在后面就暗示必须串行。存在不同路径时写明选择条件及产物差异，不能把互斥步骤拼成必经链。

每个关键判断都回答：它依赖什么证据、如何处理不确定性、失败会留下什么、用户如何查看。指标必须有分母、粒度、时间范围和质量含义。例如“91/190 条轨迹已归属”不能改写成“人物识别准确率 47.89%”。

输出文件说明须包含生产者、消费者、路径、记录粒度、身份键、时间基准、关键字段、成功/失败含义、可视化方式。大 JSON 只列关键字段，不把完整样本反复粘贴进文档。

## 6. 文档二的可解析格式：PipelineDoc 1.0

### 6.1 容器结构

文件使用 UTF-8、CommonMark 兼容 Markdown、LF 换行。Markdown 承载讲解；指定 fence 承载严格 JSON。选 JSON 是为了复用标准解析器，避免 YAML 隐式类型和额外配置语言。CommonMark 的 fenced code block 支持 info string，解析器需检查完整 info string，而不是把所有 `json` 示例当配置。[CommonMark 规范](https://spec.commonmark.org/0.31.2/)

文档二必须依次具备：标题和范围、一个 `json pipeline-system` fence、系统概念和分支、模块正文、已知差异、证据基线。模块内部只有一个 `json pipeline-module` fence。普通示例只用 `json` 或 `text`，不进入契约解析。

模块边界严格使用独立行：`<!-- module:person_align -->` 与 `<!-- /module:person_align -->`。其他可寻址正文使用 `<!-- section:overview -->` 与对应结束标记。名称为 `[a-z][a-z0-9_\-]*`，全文件唯一。解析用 Markdown AST 的代码块和 HTML 注释节点，禁止用一个跨全文贪婪正则猜结构。

模块正文固定使用六个三级标题：`作用与判断`、`输入与前置条件`、`处理过程`、`产物与消费`、`异常、重跑与成本`、`展示与验收`。不适用的内容写明原因，不能删除标题。算法细节可用四级标题进一步展开。

模块二级标题形如 `## 11 · 人物轨迹归属`，分隔符后的文本必须与元数据 title 完全一致。前面的序号仅供文档阅读；实际排序取 order，允许用 10、20 等留出插入位置，不能把序号当模块身份。

### 6.2 系统元数据

| 字段 | 类型/规则 |
|---|---|
| `doc_id` | 固定 `extract-full-pipeline` |
| `schema_version` | PipelineDoc 协议版本，当前 `1.0.0` |
| `content_version`、`updated_at` | 内容版本及 ISO 日期 |
| `title`、`summary` | 页面系统介绍标题与摘要 |
| `code_baseline` | 40 位 commit；不能保证脏工作树内容 |
| `worktree_dirty`、`evidence_section` | 布尔；指向证据章节标记 |
| `default_route` | `routes` 中一个 ID |
| `routes[]` | `id/title/modules[]/description`；成员必须是有效模块 ID，按依赖兼容 |
| `groups[]` | `id/title/order`；页面导航分组，order 唯一 |
| `layout_profiles[]` | `id/title/description`；说明物理布局，不决定算法路线 |
| `sample_run` | 可选，只记录样本定位和核验日期，不能当运行时默认统计 |

算法 route 与文件 layout 独立：同一 Scheme A 运行可能保存为原始 `annotations/...` 布局，也可能整理为 `captions/...` 布局。不能靠存在 `captions/` 推断算法版本。

### 6.3 模块元数据

| 字段 | 类型/规则 |
|---|---|
| `id/title/order/group` | 稳定 ID；中文名；全局唯一整数顺序；有效 group ID |
| `lifecycle` | `active/optional/legacy/deprecated/external` |
| `implementation` | `existing/external/planned`；与生命周期独立 |
| `summary` | 一句话用途，直接展示于卡片 |
| `depends_on[]` | 必需模块引用；描述本模块声明路径的依赖 |
| `optional_depends_on[]` | 增强/对照依赖；不阻止基本展示 |
| `inputs[]` | 输入产物 ID，必须可解析到某模块的 outputs |
| `source_refs[]` | 仓库相对文件路径；允许明确 `../` 指向仓库外证据，禁止变成任意文件读取接口 |
| `evidence[]` | `code/sample/design/unknown` 的非空子集 |
| `outputs[]` | 本模块拥有的产物契约对象，定义见下节 |
| `view` | `enabled/renderer/adapter/filters[]/primary_artifact` |

`order` 是阅读顺序，依赖图是执行约束；不能用 order 推导数据流。`depends_on` 同时表达所有列入 inputs 的必需来源；选配输入所属生产者列在 optional_depends_on，并在正文注明。互斥路线分别放独立模块或明确可选分支，不能让读取器自动执行任何路线。

`view.renderer` 是文档三中的受控组件类型；`view.adapter` 是已注册数据读取器标识，均不能是可执行代码、动态 import 或 shell 命令。本文档组规定名字，不代表对应适配器已经实现。

### 6.4 产物契约

每个 outputs 元素必须有：

| 字段 | 规则 |
|---|---|
| `id/title/kind` | 全文唯一稳定 ID；中文标题；`json/jsonl/structured/directory/media`；structured 表示入口明确兼容 JSON 与 JSONL，需适配器核验实际格式 |
| `paths` | 映射：layout profile ID → 相对路径模式数组 |
| `record_key[]` | 原始行/实体键；无行记录可为空；运行、视频维度由网站补齐 |
| `timebase` | `source/global_local/shot_local/segment_local/mixed/none` |
| `schema` | 真实 schema 字符串或显式 `unversioned`、`mixed`；不能猜测 |
| `required` | 对该模块当前运行方式是否必产出；false 为选配 |

记录关键字段和消费者放在紧邻正文；同一个产物不在其他模块重复定义。`paths` 是读取定位契约，不是强制搬迁现有产物。

路径占位符 `{video}/{scope}/{shot}/{subject}` 来自明确的运行绑定或已经解析的实体，不取用户原始输入直接拼接。允许 glob `*`，默认禁止 `**` 扫全工作区。`custom` profile 的 `{output}` 等占位符由后端运行配置绑定至该模块的真实输出根；整文件占位符如 `{source_video}/{asr_file}` 也必须先解析为已登记 root_id + 相对路径，不能直接信任外部绝对路径。`{impl}` 等方案占位符必须从明确配置的允许集合选择。未绑定应报告 `unconfigured`。

同一 profile 有多个模式时必须显式选定或验证它们是同一份内容的镜像；不能“找到第一个就用”，不能合并不同运行的同名文件。directory 类产物需要适配器限定扩展名、深度、读取数量。路径不符时新增 profile/绑定，不改写历史数据。

### 6.5 状态、唯一键和引用

模块是否存在、运行是否完成、资产是否可信是三个维度。统一运行状态为 `unconfigured/not_applicable/not_run/running/partial/succeeded/failed/unknown`；质量状态由产物适配器独立提供 `unreviewed/candidate/accepted/ambiguous/rejected/unknown`。仅凭缺文件不能推断 `failed`，仅凭存在文件不能推断 `succeeded`。

实体规范键使用对象：`{run_id, video_id, scope_id, kind, local_id}`。必须保留原始键；对数字 shot ID 和 `SHOT_00768` 的归一化发生在适配器，不修改源文件。多段文本、轨迹、音频之间用实体引用和产物 ID 关联，避免网页靠文件名猜身份。

### 6.6 版本和弃用

补充文字、新增可选字段、增加现有渲染器的模块，更新 content_version。改变必填字段、标记语法、类型或状态语义，升级 schema_version 主版本并提供兼容读取器。非破坏性协议扩展升级次版本。

模块退出展示时先 `view.enabled=false` 或 `lifecycle=deprecated`，保留 ID、解释和旧链接落点。新配置要同步移除 route 引用，或保留为历史路线；检查下游依赖再物理删除。删页面模块不删除历史运行文件。改模块名称不用换 ID。
